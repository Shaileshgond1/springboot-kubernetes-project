This note summarizes what I practiced and understood from Deployment,
Service, NodePort, kubectl port-forward, and Ingress on Minikube running
inside an EC2 instance.

1. STARTING KUBERNETES SETUP
----------------------------

I already had a Spring Boot application running on port 8080.

Deployment:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: myapp-container
          image: sw1236/springboot-kubernetes-project
          ports:
            - containerPort: 8080

Important:
- Deployment creates and manages 3 Pods.
- The Pods have the label:
    app: myapp
- The container is expected to have the Spring Boot application listening
  on port 8080.
- containerPort: 8080 documents the container port; it does not itself
  force Spring Boot to listen on 8080.


2. KUBERNETES SERVICE
---------------------

I created this Service:

apiVersion: v1
kind: Service
metadata:
  name: serv
spec:
  selector:
    app: myapp
  type: NodePort
  ports:
    - port: 8080
      targetPort: 8080
      nodePort: 30090

Meaning of the ports:

- port: 8080
    The port exposed by the Kubernetes Service.

- targetPort: 8080
    The port on the selected Pods where traffic is sent.

- nodePort: 30090
    The port exposed on the Kubernetes node.

Traffic:

    NodePort 30090
          |
          v
    Service 8080
          |
          v
    Pod 8080


3. WHY THE SERVICE WAS WORKING
------------------------------

I checked:

kubectl describe service serv

Important output:

Selector:                 app=myapp
Type:                     NodePort
IP:                       10.97.119.222
Port:                     8080/TCP
TargetPort:               8080/TCP
NodePort:                 30090/TCP
Endpoints:                10.244.0.4:8080,10.244.0.6:8080,10.244.0.5:8080

The Endpoints proved that the Service successfully found all 3 Pods.

The Service selector:

    app=myapp

matched the Deployment Pod labels:

    app: myapp

Therefore the Service had 3 backend endpoints.


4. CHECKING PODS
----------------

Useful command:

kubectl get pods -l app=myapp -o wide

This shows:
- Pod names
- Ready status
- Pod IPs
- Node

The Pod IPs can be matched with the Service endpoints.

Example concept:

    Pod A -> 10.244.0.4:8080
    Pod B -> 10.244.0.5:8080
    Pod C -> 10.244.0.6:8080


5. KUBECTL PORT-FORWARD TO THE APPLICATION SERVICE
---------------------------------------------------

I used:

kubectl port-forward --address 0.0.0.0 service/serv 30090:8080

Meaning:

    EC2 :30090
         |
         v
    kubectl port-forward
         |
         v
    Service "serv" :8080
         |
         v
    One of the backend Pods :8080

Important:
- --address 0.0.0.0 makes kubectl listen on all network interfaces.
- Without it, port-forward normally listens only on localhost.
- This was useful because the Kubernetes environment was running inside EC2.
- kubectl port-forward is mainly useful for development/testing/debugging.
- If the port-forward process stops, the forwarding stops.


6. NEXT STEP: INGRESS
---------------------

After practicing Deployment and Service, I moved to Ingress.

Ingress is used to manage HTTP/HTTPS routing into Kubernetes Services.

Basic architecture:

    Client
       |
       v
    Ingress
       |
       v
    Service
       |
       v
    Pods

Ingress can later be used for:
- Host-based routing
- Path-based routing
- HTTP/HTTPS
- TLS
- Routing multiple applications through one entry point

----------------------

Command:

This tells Kubernetes that an NGINX Ingress Controller is available.

The Ingress resource can specify:

    ingressClassName: nginx


9. CREATE THE INGRESS RESOURCE
------------------------------

I created ingress.yml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: serv
                port:
                  number: 8080

Apply it:

kubectl apply -f ingress.yml

Output:

ingress.networking.k8s.io/myapp-ingress created

Check it:

kubectl get ingress

Observed:

NAME            CLASS   HOSTS   ADDRESS   PORTS
myapp-ingress   nginx   *                 80

The empty ADDRESS was not a problem in this Minikube-on-EC2 setup.
The Ingress resource was created and the NGINX controller was running.


10. WHAT THE INGRESS YAML MEANS
--------------------------------

apiVersion: networking.k8s.io/v1
    Uses the current Kubernetes Ingress API.

kind: Ingress
    Creates an Ingress resource.

metadata:
  name: myapp-ingress
    Name of the Ingress object.

spec:
  ingressClassName: nginx
    Tells Kubernetes to use the NGINX Ingress Controller.

rules:
  - http:
      paths:
        - path: /
          pathType: Prefix
    Any HTTP request matching "/" is handled by this rule.

backend:
  service:
    name: serv
    port:
      number: 8080

    The Ingress sends matching traffic to:
        Service "serv" on port 8080.

So the complete routing is:

    Client
       |
       v
    NGINX Ingress Controller
       |
       v
    myapp-ingress
       |
       v
    Service "serv":8080
       |
       +-------------------+
       |                   |
       v                   v
    Pod :8080           Pod :8080
       |
       v
    Pod :8080


11. CHECK THE INGRESS SERVICE
-----------------------------

Command:

kubectl get svc -n ingress-nginx

Observed:

NAME                                 TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)
ingress-nginx-controller             NodePort    10.109.4.203    <none>        80:32733/TCP,443:32625/TCP
ingress-nginx-controller-admission   ClusterIP   10.106.61.111   <none>        443/TCP

This is very important.

Minikube automatically created the Ingress Controller Service as a NodePort.

The mapping is:

    Service HTTP port 80  -> NodePort 32733
    Service HTTPS port 443 -> NodePort 32625

I did NOT manually create NodePort 32733.

Minikube's Ingress addon created it automatically.


12. UNDERSTANDING 80:32733
--------------------------

This:

    80:32733/TCP

means:

    Service port = 80
    NodePort     = 32733

So direct NodePort traffic can be:

    Minikube IP :32733
          |
          v
    Ingress Controller Service :80
          |
          v
    NGINX Ingress Controller

14. IMPORTANT DIFFERENCE: NODEPORT VS PORT-FORWARD
---------------------------------------------------

NodePort:

    Minikube-IP:32733
           |
           v
    Ingress Service :80
           |
           v
    NGINX Ingress
           |
           v
    Application Service
           |
           v
    Pods

Port-forward:

    Local/EC2 port
           |
           v
    kubectl port-forward
           |
           v
    Kubernetes Service port
           |
           v
    Pod/Service


15. PORT-FORWARDING THE INGRESS CONTROLLER
-------------------------------------------

The correct command we discussed is:

kubectl port-forward --address 0.0.0.0 \
  -n ingress-nginx \
  service/ingress-nginx-controller \
  8080:80

Or on one line:

kubectl port-forward --address 0.0.0.0 -n ingress-nginx service/ingress-nginx-controller 8080:80

This is CORRECT.

Meaning:

    EC2 :8080
         |
         v
    kubectl port-forward
         |
         v
    ingress-nginx-controller Service :80
         |
         v
    NGINX Ingress Controller
         |
         v
    myapp-ingress
         |
         v
    serv :8080
         |
         v
    Pods :8080


16. WHY 32733 IS NOT USED IN THE PORT-FORWARD COMMAND
------------------------------------------------------

It is important not to confuse NodePort with Service port.

The Ingress Controller Service has:

    80:32733

where:
    80    = Service port
    32733 = NodePort

When using:

kubectl port-forward service/ingress-nginx-controller 8080:80

kubectl is forwarding to the SERVICE PORT 80.

Therefore:

    8080:80

is correct.

This is NOT:

    8080:32733

and it is NOT:

    32733:8080


17. EXAMPLE OF THE PORT-FORWARD COMMAND
---------------------------------------

Command:

kubectl port-forward --address 0.0.0.0 -n ingress-nginx service/ingress-nginx-controller 8080:80

Meaning:

    Port on EC2/listening side = 8080
    Port on Kubernetes Service  = 80

Then:

    EC2 Public IP:8080
             |
             v
    kubectl port-forward
             |
             v
    ingress-nginx-controller:80
             |
             v
    NGINX Ingress
             |
             v
    serv:8080
             |
             v
    Pods


18. WHY --ADDRESS 0.0.0.0 MATTERS
----------------------------------

Without:

    --address 0.0.0.0

kubectl port-forward generally listens only on localhost.

With:

    --address 0.0.0.0

it listens on all interfaces.

This was important in the EC2 setup because the EC2 instance needed to
accept the incoming connection on the forwarded port.

However, the EC2 Security Group must also allow the required TCP port.


19. IP FORWARDING VS PORT FORWARDING
------------------------------------

These are different concepts.

IP forwarding:

    sudo sysctl -w net.ipv4.ip_forward=1

This enables the Linux kernel to forward IP packets between interfaces.

Port forwarding with kubectl:

    kubectl port-forward ...

This creates a specific application/network connection from a local
listening port to a Kubernetes Pod or Service.

For the Minikube Ingress setup we practiced, manual Linux IP forwarding
was not required just to enable the Ingress addon.

The important thing was:
- Enable the NGINX Ingress Controller.
- Create the Ingress resource.
- Understand how the Ingress Controller Service is exposed.
- Use the appropriate NodePort or kubectl port-forward for testing.

24. KEY THINGS TO REMEMBER
--------------------------

1. Deployment creates/manages Pods.

2. Service provides stable networking to Pods.

3. Service selector connects the Service to Pods through labels.

4. targetPort is the Pod/application port.

5. nodePort exposes a Service through a port on the Kubernetes node.

6. Ingress is an HTTP/HTTPS routing layer.

7. An Ingress resource by itself does not process traffic.
   An Ingress Controller must be installed.

8. Minikube's ingress addon installed the NGINX Ingress Controller.

9. Minikube automatically created the Ingress Controller NodePort:
       HTTP 80 -> 32733
       HTTPS 443 -> 32625

10. kubectl port-forward to a Service uses the Service port, not its
    NodePort.

11. Therefore this is correct:

    kubectl port-forward --address 0.0.0.0 \
      -n ingress-nginx \
      service/ingress-nginx-controller \
      8080:80

12. This direct Ingress test worked:

    curl http://192.168.49.2:32733

13. The current working Kubernetes application flow is:

    Ingress
       ->
    Service
       ->
    Deployment-managed Pods
